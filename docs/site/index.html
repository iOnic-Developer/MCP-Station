One source.
Room for each account.

Keep the integration code together without mixing the configuration that makes each account yours.

  1. 01

    Bring a service in.

    Start with a bundled integration or build a module for your API. Inspect the source and the tools it exposes.

  2. 02

    Make the account explicit.

    Reuse one source with separate settings and endpoints. New accounts start blank, disabled, and untested—not with copied credentials.

  3. 03

    Test. Enable. Connect.

    Review the configuration, run the available test, then enable the endpoint. Authorize your compatible client for the account you selected.

Shared source, shared responsibility. Editing or reloading integration code affects all of its accounts. Separate settings are not process isolation.

Keep it close

Your server. Your everyday workspace.

Self-host with Docker and persistent storage. Install the web app where your browser supports it over HTTPS. It’s a PWA, not a native desktop app or offline access to private content.

Plan your setup ↗

Control starts with clarity

Self-hosted.
Not trust-free.

Keep the station on infrastructure you control. Be deliberate about the code you run and the context you share.

Read the account boundaries ↗
One administrator, not many tenants.
Service accounts are configurations—not separate user logins. The station administrator can manage every account.
Installed modules are trusted code.
Modules run in the station process. Review source and permissions; account scoping is not a sandbox. Management access and master tokens carry broad authority.
Know where assistant context goes.
Conversations, relevant source, station context, and tool output can go to your selected AI provider or gateway; self-hosting the station does not keep a cloud model’s processing local. Provider billing and privacy terms apply. Keep secrets in settings, not chat.
